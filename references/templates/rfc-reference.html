Decision Brief

Fictional example. Paths, commands, product policy and approval are illustrative. No customer study, benchmark or real approval is claimed; verify each against the target project before use.

Recommendation

Let owners rename saved reports from the existing report detail page. Preserve the current name when validation fails, and prevent one editor from overwriting another editor's newer name.

Largest risk

A read-then-write revision check can lose a concurrent edit. Use one conditional database update and exercise two clients starting from the same revision.

Decision needed

None in this example. Its hypothetical product policy is explicit: trim outer whitespace, allow 1–80 Unicode code points, and restrict renaming to the report owner. Actual products must confirm their own policy. Impact baseline and adoption remain unknown.

Appendix

Codebase Findings

Assumed example context: the project has report ownership, a numeric revision, an authenticated PATCH route, domain/API tests and a Playwright harness. An actual RFC must cite the inspected files and commands establishing these facts; unavailable infrastructure is not silently assumed.

Architecture

Report detail → authenticated PATCH → normalize and validate name
                                      → owner + expected revision conditional update
                                      → 200 updated report / 403 / 409 / 422

The client updates displayed data only after 200. On 422 it keeps the editor and identifies the invalid field. On 409 it keeps the draft, offers reload, and requires an explicit retry against the newly read revision.

Key Decisions

Chosen: atomic revision-guarded update. It preserves a newer edit and surfaces the conflict to the user. Alternative: last-write-wins is simpler but can silently discard another owner's edit. Choose it only if that loss is an explicitly accepted product behavior.

Reuse the existing report detail pattern and owner check. A new modal library or generic rename framework is unnecessary for this one surface unless an existing repository convention requires it.

Data Model

No new table in this example. The existing report has id, owner_id, name and integer revision. Update only where the owner and expected revision match; increment revision in the same statement. A denied, invalid or stale write changes neither name nor revision.

If a real repository lacks a revision, plan and verify its migration before using this approach. Do not claim this no-migration assumption as an inspected fact.

API

PATCH /api/reports/:id takes { name, expected_revision }. Return 200 with the canonical name and new revision, 422 with a field error for invalid input, 403 for a nonowner and 409 for an owner's stale revision. Perform authorization before returning conflict data; never disclose another owner's report through the recovery response.

Test levels in scope

  • Domain: trim, blank and Unicode boundaries; input report remains unchanged on failure.
  • Integration: real authenticated owner/nonowner requests and simultaneous conditional writes against the test database.
  • Browser E2E: existing detail-page entry, successful rename, validation recovery, two clients and preserved list-return context.

2Recover from a concurrent rename without losing draftsS

Outcome: An owner understands a concurrent edit and explicitly chooses whether to reload or retry.

Acceptance Criteria

  • AC4: two owner clients submit different names from revision 4; exactly one receives 200 and one 409. Stored name equals the successful request and revision is 5.
  • AC5: the losing client retains its draft and sees the conflict. Reload displays the stored name/revision; explicit retry uses revision 5 and succeeds at revision 6 if no further edit occurs.
  • AC6: conflict handling leaves navigation/filter context intact and never weakens the nonowner 403 rule.

Approach: Extend the existing editor with reload/retry actions. Fetch current state only through the authorized report route. Test simultaneous API writes against the real test database and two browser contexts; avoid sleep-based ordering.

Resolved Questions

Q: overwrite a newer name automatically? A: no; the example policy preserves concurrent edits and requires explicit retry. This is a fictional confirmed decision, not a real user's approval.

Q: what counts toward 80 characters? A: Unicode code points after trimming outer whitespace. Client and server share that policy and boundary tests. A different real product policy must replace both.

Remaining limitations: adoption, baseline rename frequency and supported production browser matrix are unknown; no benchmark or impact result is invented.
