## Goal

Verify the current integrated UI against acceptance criteria and realistic edge states, then record a current QA gate without loading code-review or ship instructions.

## How

1. Confirm current HEAD, acceptance criteria, affected routes, platform, and the Design Critique artifact. Use Quick, Focused, or Full depth from the durable route; do not recompute safety from task kind alone.
2. Read and execute `qa.md`. Run assertion-driven checks for primary, empty, boundary, error, navigation, responsive, and accessibility behavior that applies to the change.
3. An unavailable app, auth flow, database, seed, or required service is `blocked`, never `passed` or `skipped`. Preserve the exact environment failure and smallest remediation.
4. Execute the charter and classify every finding. No unresolved Critical or High finding may receive a passing verdict; QA does not edit source.
5. Retain each deterministic/browser assertion result and any supporting screenshots under `.pm/dev-sessions/{slug}/qa/evidence/`, then hash-bind them through the report's receipts. Every assertion row has `finding_ids`: empty for general coverage or the exact findings it probes. For a passing latest run, reproduce the session's exact acceptance criteria and ordered design critical states in `coverage`, binding every row to passed current-run assertion IDs. The tier is fixed by routed size (XS quick, S focused, M/L/XL full). If `task.design_context.ui_impact` is true or `task.risk.ui > 0`, require a successful current-run browser receipt and browser-backed critical-state assertions. Each screenshot belongs to exactly one receipt with the same run and commit; limit screenshots to 15 per run.
6. Save the only QA report at `.pm/dev-sessions/{slug}/qa/report.json`; keep run history inside that standalone artifact. Before replacing an existing report for re-verification, copy its exact bytes to `qa/evidence/report-run-{previous-run}.json`, bind that path/hash/size from the new run, and preserve every prior run, receipt, screenshot, finding evidence, and owning commit. Historical commits must resolve in Git and form an ancestor chain. Record exact fixed/still-open/new finding partitions, and bind each fixed finding to passed new-run assertions whose `finding_ids` include it. Then atomically replace `report.json`.
7. Validate a passing report with `node ${PM_PLUGIN_ROOT}/scripts/qa-report-check.js --session <absolute-session.json> --report <absolute-report.json> --commit <current-HEAD>`. Validate a `fail` or `blocked` report with the same command plus `--allow-nonpassing`; this certifies structure, not passage. Require exit 0.
8. Return every validated verdict as a strict phase result with the current commit and exactly one successful `test` evidence record pointing at the absolute canonical report. The Dev runner must record a failed or blocked attempt before any fix or re-verification; its ordered attempts are the external run-count anchor. A failed or blocked verdict creates no passing gate row. For a recorded failure, the Dev root fixes Critical/High and core-flow Medium findings, then resumes QA to re-run affected assertions and adjacent-route smoke checks; bound the loop to three attempts.
9. On the final passing verdict, update the gate manifest with `qa: passed` at current HEAD and the report path. The runner revalidates the report bytes, location, commit, verdict, score, findings, and history. Do not add Markdown-like QA sections to `session.json`.

## Done-when

- Every acceptance criterion and design critical state has a passed latest-run assertion binding; UI-scoped sessions have current browser evidence. Screenshots remain optional for non-visual/non-UI checks.
- The final verdict is Pass or Pass with concerns, with no unresolved Critical or High finding.
- The canonical report passes `qa-report-check.js` at current HEAD.
- QA gate and phase evidence are current for HEAD and validate.

**Advance:** record the result and proceed to Step 08 (Review), as selected by the runner.
