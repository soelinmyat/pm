## Goal

Verify the current integrated UI against acceptance criteria and realistic edge states, then record a current QA gate without loading code-review or ship instructions.

## How

1. Read `${CLAUDE_PLUGIN_ROOT}/references/browser-evidence-preflight.md` before browser collection. Check the retained intake method context against current tools, policy and required claims; choose a supported route/fallback early, keep platform gates intact, and reuse unchanged method context without manufacturing another PM approval request. Confirm current HEAD, acceptance criteria, affected routes, platform, and the Design Critique artifact when routed. Use Quick, Focused, or Full depth from the durable route; do not recompute safety from task kind alone. For risk-assessed XS/S UI without standalone critique, enable visual layers. Inspect desktop and narrow layout and exercise native keyboard focus/navigation on affected controls. Use actual CSS-scale viewport screenshots, record viewport conditions in probes, and retain distinct browser assertions for `Desktop layout`, `Narrow layout`, and `Keyboard focus and navigation` before existing design critical states. Each layout coverage row includes `screenshot_id`, naming its current screenshot in the assertion's browser receipt. Desktop and narrow dimensions must satisfy `scripts/lib/product-ui-viewport.js`; capture at CSS scale, not device-pixel or full-page scale. Combined review replaces only the separate design artifact/reviewer ceremony, not source review or release checks.
2. Read and execute `qa.md`. Run assertion-driven checks for primary, empty, boundary, error, navigation, responsive, and accessibility behavior that applies to the change.

   For the combined web route, retain each layout assertion's structured `capture` in its hash-bound execution output: `{ screenshot_id, css_width, css_height, device_pixel_ratio, scale: "css", full_page: false }`. Observe CSS dimensions and DPR from the browser during capture; do not infer them from PNG pixels. PNG dimensions must match the CSS viewport. Mobile, mixed, and unknown platforms keep their existing standalone critique and platform-specific QA.
3. An unavailable app, auth flow, database, seed, or required service is `blocked`, never `passed` or `skipped`. Preserve the exact environment failure and smallest remediation.
4. Execute the charter and classify every finding. Derive each expected result from approved intent/domain rules and independent fixtures; state the expectation source and limitations in existing evidence strings. Use condition-based completion waits, distinguish visible/operable from merely present, and check persistent outcomes where required. Assertions must reject plausible defects, including missing/duplicate/incorrect filter results; empty `every` checks do not verify non-empty scenarios. Assess the whole task and cumulative friction alongside measurable properties. The retained score is a tested-scope finding index, not certainty or coverage; explicitly name unexamined dimensions. No unresolved Critical or High finding may receive a passing verdict; QA does not edit source.
5. Retain each deterministic/browser assertion result and any supporting screenshots under `.pm/dev-sessions/{slug}/qa/evidence/`, then hash-bind them through the report's receipts. Every assertion row has `finding_ids`: empty for general coverage or the exact findings it probes. For a passing latest run, reproduce the session's exact acceptance criteria and ordered design critical states in `coverage`, binding every row to passed current-run assertion IDs. The tier is fixed by routed size (XS quick, S focused, M/L/XL full). If `task.design_context.ui_impact` is true or `task.risk.ui > 0`, require a successful current-run browser receipt and browser-backed critical-state assertions. Each screenshot belongs to exactly one receipt with the same run and commit; limit screenshots to 15 per run.
6. Save the only QA report at `.pm/dev-sessions/{slug}/qa/report.json`; keep run history inside that standalone artifact. Before replacing an existing report for re-verification, copy its exact bytes to `qa/evidence/report-run-{previous-run}.json`, bind that path/hash/size from the new run, and preserve every prior run, receipt, screenshot, finding evidence, and owning commit. Historical commits must resolve in Git and form an ancestor chain. Record exact fixed/still-open/new finding partitions, and bind each fixed finding to passed new-run assertions whose `finding_ids` include it. Then atomically replace `report.json`.
7. Validate a passing report with `node ${PM_PLUGIN_ROOT}/scripts/qa-report-check.js --session <absolute-session.json> --report <absolute-report.json> --commit <current-HEAD>`. Validate a `fail` or `blocked` report with the same command plus `--allow-nonpassing`; this certifies structure, not passage. Require exit 0. Recording the accepted QA result stores one immutable run/commit/verdict/report-digest anchor per report run in `session.json`; later checks bind those anchors to the current report or retained predecessor snapshots.
8. Return every validated verdict as a strict phase result with the current commit and exactly one successful `test` evidence record pointing at the absolute canonical report. The Dev runner must record a failed or blocked attempt before any fix or re-verification; its ordered attempts are the external run-count anchor. A failed or blocked verdict creates no passing gate row. For a recorded failure, the Dev root fixes Critical/High and core-flow Medium findings, then resumes QA to re-run affected assertions and adjacent-route smoke checks. Three unresolved rounds trigger the autonomous recovery diagnosis in `qa.md`, not a request for permission or a forced stop. Continue the same authorized scope with continuous attempt/run history until acceptance holds or a genuine dependency, product decision, or material scope/risk change blocks progress.
9. On the final passing verdict, after the runner records it, run `node "$PM_PLUGIN_ROOT/scripts/dev-session.js" gate --session <absolute session.json> --name qa`. The command revalidates the report bytes, location, commit, verdict, score, findings, and history, writes `qa: passed` at current HEAD with the report path, and writes nothing on any failure. Never hand-edit `gates.json`. Do not add Markdown-like QA sections to `session.json`.

## Done-when

- Every acceptance criterion and design critical state has a passed latest-run assertion binding; UI-scoped sessions have current browser evidence. Screenshots remain optional for non-visual/non-UI checks.
- The final verdict is Pass or Pass with concerns, with no unresolved Critical or High finding.
- The canonical report passes `qa-report-check.js` at current HEAD.
- QA gate and phase evidence are current for HEAD and validate.

**Advance:** record the result and proceed to Step 08 (Review), as selected by the runner.

Before expensive QA, preflight fixture existence and seed revisions, selectors against the built screen, unique capture names against the acceptance matrix, build/dependency setup, and the declared device/simulator state. Record the harness command and failure cause separately from a product assertion. Respect session locks and owner identity; an occupied shared simulator is an environment blocker, never permission to unlock, steal or silently switch a locked session. Repair a harness failure and rerun affected acceptance checks without inventing a product regression.

Acceptance evidence and report presentation have separate identities. Repairing HTML/layout alone does not mean acceptance behavior failed. Preserve immutable run/capture/source bindings and revalidate the report through the existing checker. If canonical JSON bytes change, its bound digest and run history still require the owning recertification protocol; never edit accepted history or claim a formatting repair passed live QA. Relevant source, dependency, fixture or environment drift requires affected QA or conservative full QA when impact is uncertain.
